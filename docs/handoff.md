# 引継ぎ：タスクビュー（UIの調査と改修）

個人環境で続きを進めるための引継ぎ資料。まずこのファイルを読み、次に `README.md` で動かし方を確認する。

## 1. これは何か

複数の案件フォルダにある `タスク一覧.md` を読んで、ブラウザに期限ビューを出す**ローカル専用・読み取り専用**のツール。
Python 3.12 の標準ライブラリだけで動く（外部パッケージなし）。`127.0.0.1` にだけ待ち受ける。

作った動機は、会話で AI に聞けば済む汎用ツールではなく、「毎朝開くだけで、案件ごとの期限・待ち・完了が一目で分かる、自分の作業に特化した道具」が欲しかったこと。

## 2. 最初に守ること

- **業務データを持ち込まない。** このフォルダのデータはすべて架空のダミー。実在の会社名・人名・案件名・チケット番号・アカウントIDは入れない。
- 画面の確認は `sample-data/`（ダミー）で行う。自分の実データで試す場合も、そのファイルをこのフォルダに入れたり、外部サービス（クラウドの AI など）に貼ったりしない。
- ダミーデータは `tools/gen_sample.py` が**実行日からの相対日付**で作る。いつ実行しても「期限切れ／7日以内／今月中／それ以降／期限未定」が出る。

## 3. 現状の仕様

### 3.1 タスク一覧.md の書式
```
## 進行中・今後のタスク
| グループ | タスク | 期限 | 由来 | 状況・メモ |
|---|---|---|---|---|
| PRJ-101 | 〜をまとめる | 10/9 | 週次定例 | 要確認：〜 |

## 他の人に待っている／他の人の宿題（把握用）
- 【PRJ-101】田中さん：仕様書の共有

## 完了
- 2026-10-02：【PRJ-101】要件一覧の初版を作成
```
- 表の列は**見出しの名前**で読む（並び順は自由）。`グループ`（別名: プロジェクト／チケット）は任意で、空欄でもよい。
- グループ列が無い・空のときは、タスク名が `名前：内容` の形ならその名前をグループにする。
- 待ち・完了の行は、先頭に `【グループ名】` を付けると同じグループに入る。
- 期限の書き方: `10/9`、`2026-10-09`、`10月中`、`11月末`、`11月`。それ以外（「確認が取れてから」等）は期限未定。`（旧：10/9）` を付けると「延長」扱い。
- メモに `要確認` や `待ち` を含むと、それぞれのバッジが出る。

### 3.2 画面
- 案件ごとのタブ（案件間は混ぜない）。
- 右上の切り替え: **期限別**（期限区分ごとのカード＋右サイドバーに待ち・完了）／**グループ別**（グループが折りたためる入れ物で、中に進行中・待ち・完了が枝線でぶら下がる）。
- 画面上部に、期限区分ごとの件数タイル5つ。

### 3.3 ファイル構成
```
task-view/
├─ docs/handoff.md     このファイル
├─ README.md           動かし方
├─ run.bat             ダブルクリック起動（ダミーデータを読む）
├─ app/
│  ├─ taskview.py      サーバー兼パーサー（約300行）
│  └─ index.html       画面（HTML・CSS・JS を1ファイルに同居）
├─ tools/gen_sample.py ダミーデータ生成
└─ sample-data/        案件A（標準）／案件B（長い題・バッジ多め・完了のみのグループ）
                       案件C_空（空状態）／案件D_件数多（20件・密度確認）
```

## 4. 課題：「入れ子にはなったが、見やすくない」

実データ7件の画面（グループ別表示）を実測した結果。**ダミーの案件Aで再計測し、改修前の基準値として記録すること。**

| 項目 | 実測 |
|---|---|
| ページの高さ | 1326px（画面は768px）。7件でスクロールが必要 |
| 1タスクの高さ | 80〜114px（タイトル・バッジ・開閉見出しがそれぞれ別の行） |
| 「状況・メモ・由来」の開閉 | 7件すべて（100%）の行に付いている |
| 補足の文字 | 11〜12px |
| 件数タイル | 5枚。グループ見出しの件数と重複 |
| バッジ | 「要確認」の赤枠がほぼ全行に付く |
| 色 | 青・灰・紫・赤・橙の5色 |

※「要確認」が全行に付くのは、下書きを全部「要確認」にしたため。ただし**常に付く前提のデザインは避ける**（下記の調査参照）。

## 5. 調査結果

調査担当（AI）がWebで調べた結果の要約。**Web検索は使えず、公式ページを直接取得できた範囲のみ。** 取得できなかった製品（Todoist／Asana／Jira／Basecamp の詳細）は「不明」。出典URLは調査担当が挙げたもので、**引用する前に自分で開いて確認すること。** 「推測」は原則からの推論で、特定の製品がそうしている確認ではない。

### 5.1 先行事例
| 製品 | 分かったこと | 出典 |
|---|---|---|
| Linear | 見出しに件数。表示項目をユーザーが選べる。My Issues の Focus は緊急度順に自動で並べる。空グループは既定で非表示 | https://linear.app/docs/display-options ／ https://linear.app/docs/my-issues |
| Things 3 | プロジェクトは小さな進捗の円で達成度を示す。期限・タグ・チェックリストは必要になるまで隅に隠す。余白は広め | https://culturedcode.com/things/features/ |
| Notion | グループごとに表示／非表示。空グループを隠せる。プロパティ表示はビューごとに切替 | https://www.notion.com/help/views-filters-and-sorts |
| GitHub Projects | グループ見出しに件数と数値フィールドの合計。フィールドの表示／非表示 | https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-table-layout |

共通して見られた傾向（確認できた範囲）: 表示項目は選べて既定は少なめ／任意項目は隠して必要時に出す／見出しは件数など数値のみ／進捗は小さな図形1つ／状態で並べて自動で上に出す。避けられていた: 全属性の常時表示、大きな円グラフ・ゲージ。

### 5.2 一般原則
- 標識（バッジ）は「ノイズや散らかりを生む」。重要度と頻度を確かめてから足す。対応不要なら装飾せず文字のままにする（5〜6個を超えると集中を損なう）。
  https://www.nngroup.com/articles/indicators-validations-notifications/ ／ https://carbondesignsystem.com/patterns/status-indicator-pattern/ ／ https://atlassian.design/components/lozenge/usage
- 毎行の開閉（アコーディオン）は、情報の断片化・操作コスト・比較のしにくさを生む。ほとんどの内容が必要な場面では避ける。多用するなら「すべて開く／閉じる」を付ける。
  https://www.nngroup.com/articles/accordions-on-desktop/ ／ https://www.nngroup.com/articles/progressive-disclosure/
- ダッシュボードは1画面に収め、量は長さや位置で伝え、色は補助にとどめる。
  https://www.nngroup.com/articles/dashboards-preattentive/
- 流し読みでは行頭の語が最も見られる。各行の最初の2語で要点が伝わるようにする。
  https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/
- 色だけで意味を伝えない（WCAG 1.4.1）。通常の文字は背景とのコントラスト4.5:1以上（WCAG 1.4.3）。
  https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html ／ https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html
- 日本語UI（デジタル庁デザインシステム）: 本文・UIは16px以上（14pxは補足のみ）、情報量優先の管理画面では行間120〜130%。
  https://design.digital.go.jp/dads/foundations/typography/
- 相対表記（あと24日）は、絶対日付をツールチップなどで併記する（GitLab Pajamas）。
  https://design.gitlab.com/content/date-and-time/
- 近接・共通領域（Gestalt）: 近くにあるものは同じグループに見える。枠や背景で囲むとグループに見える。
  https://www.nngroup.com/articles/gestalt-proximity/ ／ https://lawsofux.com/law-of-common-region/

### 5.3 確認できなかったこと（要追加調査）
- 階層リストの**枝線が有効か**を示す直接の根拠（インデントと余白だけで足りる可能性が高い、という推測にとどまる）。
- 「月中」や条件付き期限の見せ方、期限切れの強調の根拠。
- 件数タイルが個人用リストで不要かどうかの直接の根拠。
- サイドパネルとホバーの比較。長いタスク名の折り返し・省略の指針。
- Todoist／Asana／Jira／Basecamp の具体的な設計。

## 7. 実装メモと既知の問題

- **サーバーを再起動しないとパーサーの変更が反映されない。** 画面（`index.html`）は毎回読み込み直されるが、`taskview.py` は起動時のコードのまま動く。コードを直したら、古いサーバーを止めて起動し直す。「コード変更で自動再読み込み」を入れる案あり。
- **フラグ判定が部分一致。** メモに「待ち」「要確認」の文字が含まれるだけでバッジが付く（例:「承認待ち」の説明文でも「待ち」が付く）。メモ先頭の `待ち：` `要確認：` の接頭辞で判定する方が安全。
- 年なしの日付（`10/9`）は、基準日（最終更新日）から半年以上前になる場合だけ翌年とみなす。年またぎの境界は未検証。
- 「N月中」「N月」は月末日に換算して並べ替える。表示は原文のまま。
- 「期限別／グループ別」と選択中の案件は、ブラウザの localStorage に記憶している（キー: `taskview.view`、`taskview.project`）。
- `.bat` は**中身をASCIIのみ・CRLF改行**にする。日本語や LF 改行だと cmd が誤動作する（実際に起きた）。日本語を含むパスは、ワイルドカードや `%~dp0` で組み立てる。
- 画面は XSS を避けるため、すべて `textContent` 系（`createTextNode`）で描画している。`innerHTML` を使わない方針を維持する。
- 過去に直したバグ: 表の先頭セルが空の行を区切り行と誤判定して消していた（ダミーの案件Aの「経費精算の申請」で発覚）。

## 8. 進め方（推奨）

1. `README.md` に従って起動し、ダミーの案件A〜Dを見る。
2. 案件Aで現状の実測値（第4章の表）を取り直して、このファイルか別メモに残す。
3. 第5.3章の「確認できなかったこと」のうち、枝線の要否と曖昧な期限の見せ方を追加調査する。
4. 第6章の方針を、小さい単位（例: バッジ → 開閉 → タイル → 期限表記 → 文字サイズ）で入れ、毎回、受け入れ基準を測って記録する。
5. 全部入れたあと、自分の実データ（手元の環境だけで）で使ってみて、見づらい点を足す。

## 12. 2026-10-07 色分けの丸をなくし、全タブを同じ1行の形にそろえた

- SIR0 の指摘: 「タスクの頭の丸と文字の色が何を分けているのか分からない」（期限区分の 5 色、凡例なし）。
- 対応: 丸・枝線・件数タイル・色つきバッジをなくした。期限は右端の文字「10/9 ・ あと2日」「10/4 ・ 3日超過」「10月中 ・ あと24日」「レビュー返信後 ・ 延長」「—」で伝える。色は期限の文字の赤（期限切れ）と橙（7日以内）だけ。「? 未確認」「待ち」は枠つきの灰色の文字。
- 期限別: 区分の見出し（期限切れ／7日以内／今月中／それ以降／期限未定）の下に1行ずつ、その下に待ち・完了（折りたたみ）。右サイドバーは廃止。
- グループ別: 見出し「PRJ-101  進行中 5 ・ 待ち 2   完了 2/7」の下にタスク → 待ち → 完了（折りたたみ）。
- 実測（1366×768）: 1行 43px（長いタイトルは2行 67px で省略）。案件A グループ別 1583px → 1148px、期限別 1706px → 1141px。行ごとの開閉見出し 0。文字色は 4 色（本文・補足・赤・橙）。
- まだ: 受け入れ基準1（案件Aが 768px でスクロールなし）は未達。グループ見出しの余白やメモの扱いをもう一段詰めるか、SIR0 が使ってから決める。
- 次の候補: 待ちに「いつから」（日数表示）、最終更新が古いときの知らせ。
